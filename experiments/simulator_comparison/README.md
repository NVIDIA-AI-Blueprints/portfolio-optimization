# Simulator Comparison

Runs the scenario simulators on identical inputs and records, per trial, forecast origin, arm, and horizon, how long the arm took to generate its scenarios and how well they forecast the realized returns over the horizon of the assets and of random portfolios of them (`scores.py`).

- **Arm**: one simulator on one device: `no_fit-cpu` (the look-back window's own returns), `gaussian-cpu`, `kde-cpu` (scikit-learn), `kde-gpu` (cuML), `jointfm-cpu`, and `jointfm-gpu`. The config names the JointFM arm `jointfm`. It runs as `jointfm-cpu` or `jointfm-gpu`, depending on the device the service selected in `.env` reports. The three dependence swap arms, `swap-jointfm-window`, `swap-window-jointfm`, and `swap-window-window`, recombine two of these simulators instead of simulating ([Dependence swap arms](#dependence-swap-arms)). Two more arms attribute the rebalancing readings: `jointfm-historical`, JointFM's scenarios on the window's mean, and the positive control `window-independent`, the window's returns with all dependence removed ([Rebalancing attribution](#rebalancing-attribution)).
- **Horizon**: the number of trading days after the origin over which a scenario and its outcome run, one of the config's `horizons`. A rebalanced portfolio is held for weeks, so day-one scores cannot see what builds up over them: volatility clustering, mean reversion, and dependence that changes in a sell-off. [Horizons](#horizons) describes how each arm forecasts them.
- **Returns**: every return is a simple return, `P_t / P_{t-1} − 1`: the look-back window every simulator fits, the scenarios, the realized outcomes, the rebalancing optimizer, and its backtest. A portfolio's return is then the weighted sum of its assets' returns, which stays exact for short positions, whose loss has no floor: a long-short portfolio can lose more than its capital. JointFM still forecasts log prices and converts their difference into a simple return ([Horizons](#horizons)). Results files recorded with log returns cannot be resumed or reported; rerun them from scratch.
- **Portfolio size**: the number of assets a scored portfolio holds, a reporting dimension of its own. An equal-volatility portfolio's variance scales with (1 − ρ)/N + ρ for N assets of mean pairwise correlation ρ, so size 1 reads the per-asset distributions alone and larger sizes read the dependence between assets ever more.
- **Trial**: a seeded draw of `assets` price columns and `origins` forecast origins. Every arm gets the same assets, look-back window, and scenario seed at each origin, so arms differ only in the simulator. An origin needs `origin_history` returns before it, at least the look-back window's `look_back`, and `forward` returns after it. Only the draw reads `origin_history`, so two configs that differ only in `look_back` draw the same trials, origins, and scenario seeds ([Paired comparison](#paired-comparison)). Only the scores read the forward returns; no arm sees them.

## Run

A YAML file in [`configs/`](configs/) describes a run completely: data, trial and origin counts, universe size, windows, scenario count, seed, arms, portfolio sizes, and horizons. Services and GPUs are not part of it: the arms read `.env` through the library's defaults, as every user of the library does. [`config.py`](config.py) validates it and describes every field. Every field must be present, and unknown keys are refused. The same file drives the report, which reads the results from its `output`. Copy a shipped config to change an experiment, for example to run only the CPU arms on a host without a GPU.

Two sets of configs run the experiments. The pilot set runs at a small size to measure cost per arm and noise, and to recheck a newly served checkpoint cheaply. The full set runs at the size whose intervals resolve the readings a study records. Each set is a base config and a risk-averse twin, and the pilot set adds a next-day and a long-history twin. Each twin differs from its base in one setting and its output files, so its readings pair with the base's trial by trial ([Paired comparison](#paired-comparison)).

| Config | Purpose |
| --- | --- |
| [`pilot.yaml`](configs/pilot.yaml), [`full.yaml`](configs/full.yaml) | The base: every simulator, the [dependence swap arms](#dependence-swap-arms), and the [rebalancing attribution](#rebalancing-attribution) arms, in the scenario comparison and the rebalancing backtest |
| [`pilot_next_day.yaml`](configs/pilot_next_day.yaml) | The base scored at the next day only, so JointFM's next day comes from a next-day-only request ([Horizons](#horizons)) |
| [`pilot_long_history.yaml`](configs/pilot_long_history.yaml) | The base with a longer look-back window for every arm of the scenario comparison, at the same origins |
| [`pilot_risk_averse.yaml`](configs/pilot_risk_averse.yaml), [`full_risk_averse.yaml`](configs/full_risk_averse.yaml) | The base with a base risk aversion high enough for the CVaR term, not the expected returns, to decide the rebalancing weights; only its rebalancing backtest differs |
| [`devices.yaml`](configs/devices.yaml), [`devices_pilot.yaml`](configs/devices_pilot.yaml) | The [CPU-against-GPU experiment](#cpu-against-gpu) on the full set's backtest, and its one-trial pilot (`task experiments:devices`); a configuration of its own kind, which names the base it reads |
| [`readout.yaml`](configs/readout.yaml) | Checkpoint readout: the served checkpoint's JointFM against `no_fit` alone, at the next day only and without a backtest, on the full configuration's trials and origins, so its rows pair with the full run's next day (`task experiments:readout`) |

The JointFM arm and the cuML arm read `.env` in the repository root, the file the library's README describes: its JointFM selector picks the service, and `CUDA_VISIBLE_DEVICES` picks the GPU. The JointFM arm takes its expected returns from its own scenarios, the library's default (`JointFMSettings.expected_return="scenario"`); the other arms use the look-back window's mean, which is also what their scenarios are centered on. To compare JointFM on both devices, start a service on each, serving the same checkpoint. Run the config with `.env` pointing at one, then point `.env` at the other and run the same config again. The second run adds the other device's JointFM arm to the same results file and skips every row already in it. The runner refuses JointFM arms whose services serve different checkpoints. Before every JointFM call it checks that `.env` still selects the service recorded at session start, so a selector switched during a session stops the run instead of recording the other device's calls under this arm.

```bash
task experiments:pilot                       # the pilot set: every experiment at a small size, resuming its results
task experiments:pilot-fresh                 # the pilot set: delete its outputs, run every experiment
task experiments:full                        # the full set: every experiment at full size, resuming its results
task experiments:full-fresh                  # the full set: delete its outputs, run every experiment
task experiments:all CONFIG=experiments/simulator_comparison/configs/full.yaml    # one config: run and report everything
task experiments:run CONFIG=experiments/simulator_comparison/configs/full.yaml
task experiments:universe-sizes CONFIG=experiments/simulator_comparison/configs/full.yaml    # universe-size backtests, then the blog
task experiments:devices GPU_URL=http://127.0.0.1:8080 CPU_URL=http://127.0.0.1:8081    # CPU against GPU, resuming its results
task experiments:readout-fresh               # the served checkpoint's readout from scratch: scenario comparison and report
```

`experiments:readout` runs the scenario comparison and report of [`readout.yaml`](configs/readout.yaml), resuming its results file; `experiments:readout-fresh` first deletes its outputs. A results file holds one checkpoint, because the runner refuses to resume it against a service that reports another, so read each new checkpoint with the `-fresh` variant, and copy the report folder away first to keep the previous one.

`experiments:pilot` and `experiments:full` run every experiment of their set: `experiments:all` of the base, the rebalancing backtest of the risk-averse twin, and the paired comparison of the two backtests. `experiments:pilot` also runs the scenario comparisons and reports of the next-day and long-history twins and pairs each with the base. Their `-fresh` variants first delete every output of the set's configs.

`experiments:fresh` deletes every output the config names (scenario results, report, and blog figures, rebalancing results, report, and universes, universe-size results and universes; [`clean.py`](clean.py) prints each path) and then runs `experiments:all`: the scenario comparison, its report, the rebalancing backtests with their report, the [universe-size backtests](#universe-sizes), and the [blog figures](#blog). Use it after a change of code or library defaults, which the resumable runs would otherwise refuse or mix into old results. To continue an interrupted `experiments:fresh`, run `experiments:all`, which resumes every results file; rerunning `experiments:fresh` would delete what was already measured.

Without Task, the same run is `uv run --extra cuda13 --extra jointfm --extra experiments python -m experiments.simulator_comparison --config <config>`.

A progress bar on stderr counts forecast origins against the whole run, so a resumed run starts at the origins already in the results file, and shows each arm's latest generation time. The rebalancing and universe-size bars count runs the same way. When stderr is not a terminal, it refreshes once a minute so a log file stays short.

Run the arms on an otherwise idle host. The arms at one origin run one after another, but other load on the CPU or the GPUs still shifts their timings.

## Results

Results go to the config's `output`; the shipped configs write to the git-ignored `results/` directory. The file has one row per (trial, origin, arm, horizon). Its Parquet schema metadata holds the run's identity: the price file's hash, the experiment parameters, each arm's settings, the measurement columns, the host's CPU and GPU, package versions, and every JointFM service's checkpoint and device. It also holds the command line of each session that added rows.

- **Resuming**: rerunning the same config skips rows already in the file, so an interrupted run resumes, and a larger `trials` extends a finished run. Any other change to the identity, the horizons included, is refused instead of mixing conditions in one file.
- **Timing**: `seconds` is the wall time of the one call that generated an arm's scenarios at every horizon of an origin, repeated in each of its rows. With `horizons: [1]` the call is one `generate_cvar_data` call; with longer horizons it is one request for JointFM, and for every other arm its next-day call plus one one-day draw per day up to the longest horizon. For JointFM it includes the client's health request and the HTTP round trip.
- **Warm-up**: the first call of each arm in a process pays for imports, CUDA and cuML start-up, or the first connection, and is flagged `warmup`. Leave flagged rows out of timing summaries.
- **Scores**: the columns of `ScenarioScores` in `scores.py`, against the realized return over the row's horizon of h days, in units of each asset's trailing daily volatility times √h. CRPS, energy score, variogram score of order 0.5 ([Scheuerer & Hamill 2015](https://doi.org/10.1175/MWR-D-14-00269.1), which compares every asset pair's expected absolute return difference with the realized one and so reacts to wrong correlations that the energy score barely sees), spread, 50 % and 90 % interval coverage, a 20-bin PIT histogram, correlation errors against the daily returns of the look-back window and of the forward window, and the equal-weight portfolio's 95 % VaR exceedance. One column scores the arm's expected returns instead of its scenarios: `mean_correlation`, the correlation across assets of the next-day `CvarData.mean` its rebalancing runs optimize on with the realized h-day returns, 0 for expected returns that carry no information. Every arm on the window's mean reads the same value; JointFM's scenario mean is read off the next day of its multi-horizon request. Results files recorded before this column cannot be resumed or reported. Its docstring defines each column. Skill against `no_fit` needs that arm's row at the same origin, so the report computes it from the table.
- **Portfolio scores**: the columns of `PortfolioScores` in `scores.py`. At every origin, [`portfolios.py`](portfolios.py) draws five asset subsets per size of `portfolio_sizes` from the origin's scenario seed, so every arm and every horizon scores the same portfolios. Over a horizon of h days a portfolio holds its weights from the origin on, without rebalancing. Each subset carries an equal-weight portfolio, fully invested, and, where `rebalancing.cvar`'s weight, cash, and leverage bounds allow one at that size, a random long-only and a random long-short portfolio. Under the shipped bounds a long-short portfolio needs two long positions besides its shorts, so it starts at size 3. Per (kind, size) cell, the mean over its subsets of: the 95 % and 99 % VaR breaches, the CRPS in units of the portfolio's trailing daily volatility times √h, the squared standardized error, and a 20-bin PIT histogram; `portfolio_crps` averages the CRPS over every cell. At the full universe, the equal-weight cell's 95 % breach equals `ew_var_exceeded`. Results files recorded before these columns or the horizons existed cannot be resumed or reported; rerun them from scratch.

## Horizons

At every origin, each arm generates its scenarios for every horizon of `horizons` in one call ([`horizons.py`](horizons.py)), and every horizon is scored on its own.

- **JointFM** forecasts every horizon in one request. It receives the window as a log-price path, and the forecast log price h days after the origin minus the last observed one is the h-day log return, which `generate_horizon_samples_jointfm` turns into a simple return; every forecast price stays positive. The service draws each horizon independently, so scenario `s` at one horizon and scenario `s` at another are not one path; the scores never pair them.
- **Every other arm** builds its h-day scenario by compounding h independent one-day draws of its own simulator, `prod(1 + r) − 1`: the one rule that turns each baseline into an h-day forecast without new modeling. A one-day draw at or below −100 % implies a non-positive price, so the run stops on one instead of compounding it. Each day's draw comes from the arm's simulator under its own seed, derived from the origin's scenario seed. `no_fit`'s one-day scenarios are the window's fixed returns, so its daily draws resample them uniformly with replacement, `num_scen` per day. The compounded returns are read off one running product up to the longest horizon, so the longest horizon sets the number of draws.
- **The next day** is every arm's own one-day scenarios, exactly as a run with `horizons: [1]` produces them. For the simulators the comparison runs itself, the next-day rows therefore do not depend on the other horizons. JointFM's next day comes out of the multi-horizon request instead, so its draws differ from those of a next-day-only request; comparing its next-day readings with those of a `horizons: [1]` run of the same config shows whether querying more horizons changes JointFM's next-step forecast.
- **Blind spots.** The correlation references stay the daily correlations of the look-back and forward windows at every horizon, which equal the h-day correlations only when days are independent; 63 forward days cannot estimate an h-day correlation. Two origins of a trial less than h days apart have overlapping h-day outcomes, so at long horizons the breach rates' binomial bands, which count each origin once, are narrower than the data support.

## Dependence swap arms

The swap arms tell whether a difference between JointFM and the window comes from JointFM's per-asset distributions (its marginals) or from how its assets move together (its dependence). They cross the two marginal sources with the two dependence sources in a two-by-two design. Each arm is named `swap-<marginals>-<dependence>`, and `window` is `no_fit-cpu`:

| Marginals \ Dependence | Window | JointFM |
| --- | --- | --- |
| **Window** | `swap-window-window` | `swap-window-jointfm` |
| **JointFM** | `swap-jointfm-window` | `jointfm` |

- **Construction** ([`swaps.py`](swaps.py)): per asset, the scenario that holds the dependence donor's k-th smallest value gets the marginal donor's k-th smallest value. This is the Schaake shuffle ([Clark et al. 2004](https://doi.org/10.1175/1525-7541(2004)005%3C0243:TSSAMF%3E2.0.CO;2)). Every asset keeps its marginal donor's distribution exactly, and the joint rank structure (the empirical copula) is the dependence donor's. The JointFM corner is `jointfm` itself, since its own rank order leaves it unchanged.
- **The window's rows:** at the next day the window donor holds the look-back window's `look_back` rows, so both donors are first stretched to `num_scen` rows by repeating each row equally often. A run with swap arms therefore needs `num_scen` of at least `look_back`, and of at least `rebalancing.look_back_days` when the rebalancing comparison runs them. A stretched rank template repeats ranks. The ties are broken at random, independently per asset, from the origin's scenario seed.
- **The window corner** `swap-window-window` is the window's rows, stretched. It goes through the same construction as the two swaps, so it is the corner they are compared with, and its difference from `no_fit-cpu` measures what the construction itself adds.
- **Donors run next to the cells.** A config lists every swap arm's donors as arms too, and refuses the arm otherwise. The cells read their donors' scenarios at each origin and horizon, so they add no JointFM request. A cell added to a results file whose donors already ran generates its donors again from the origin's seed, without rows. A cell's time is its shuffle alone.
- **In the rebalancing comparison** each decision of a cell draws both donors' scenarios with the seed their own arms use, through the library's `rebalance_portfolio(scenario_generator=...)`. The cell then optimizes on the shuffled scenarios with the marginal donor's expected returns, so it differs from its marginal donor only in dependence. A cell with a JointFM donor sends one more JointFM request per decision.

## Rebalancing attribution

JointFM's rebalancing arm differs from the window's in two ways at once: its scenarios and its expected returns, which the library takes from the scenarios' mean. Two arms tell the two apart and show whether the backtest sees dependence at all.

- **`jointfm-historical`** optimizes on JointFM's scenarios with the window's mean as expected returns (`JointFMSettings.expected_return="historical"`). It sends JointFM's requests with JointFM's seed, so it draws exactly JointFM's scenarios. `jointfm` against it isolates the expected returns, and it against `no_fit-cpu` isolates the scenarios. It runs only in `rebalancing.arms`: in the scenario comparison its scenarios would be JointFM's and its expected returns the window's, which `no_fit-cpu` already reads. Its device is the JointFM service's, and it needs `jointfm` listed too.
- **`window-independent`**, the positive control, is the window's scenarios with each asset's rows permuted independently ([`independence.py`](independence.py)). It keeps every asset's returns, and so their distribution and mean, and removes all dependence between assets. A reading it moves beyond its noise against `no_fit-cpu` can see dependence; a reading it does not move cannot judge a simulator's dependence. Both reports draw that difference for every reading in figures of its own ([Where each arm is drawn](#where-each-arm-is-drawn)). It runs in both comparisons, at every horizon on the window's scenarios at that horizon, and needs `no_fit-cpu` listed too. Its time is its permutation alone. The permutations come from the origin's scenario seed, or the rebalancing seed, and a stream of their own.

## Report

```bash
task experiments:report CONFIG=experiments/simulator_comparison/configs/full.yaml
```

It reads the config's results file and its price file, so it can be rerun at any time, also while a run is still adding trials. Every reading is computed per horizon: each table holds every horizon in its `horizon` column, the horizon figures draw every reading over the horizons, and the other figures show the next day. The price file must be the one the results were measured on: the report compares its SHA-256 with the one the results file recorded and refuses another. It uses only trials in which every arm has every origin at every horizon, and prints how many it left out. While a session for one arm is still running, such as the CPU JointFM session, leave that arm out with `EXCLUDE=jointfm-cpu` (`--exclude` for the script) to report the finished arms over all their trials; rerun without it when the session ends. It writes its tables and plots to `<output stem>_report/` beside the results file.

- **Ranking** (`ranking.png`, `ranking.csv`): which arm gives the most realistic scenarios, by three proper scores side by side: the energy score, the variogram score, and the portfolio CRPS. Per trial and score, the simulators are ranked (lower is better), and the report gives each one's share of trials won and its mean rank. The measurement arms are not ranked, since one that won a trial would take the win from a simulator; `regime_ranking.csv` follows the same rule. The rankings are never merged into one number, because any weights between them would be arbitrary; an arm that wins on the energy score but loses on the two dependence-aware scores stands out across the row.
- **Skill** (`skill.png`, `skill.csv`): per trial, the percent reduction of the three ranking scores and of CRPS against `no_fit-cpu`, with the median and its 95 % bootstrap interval over trials.
- **Portfolio sizes** (`portfolio_sizes.png`, `portfolio_sizes.csv`, `portfolio_pit_<kind>.png`, `portfolio_pit.csv`): every portfolio reading as a curve over the portfolio size, one panel per kind. The 95 % and 99 % breach rates come with the binomial band of a calibrated forecast over the arm's origins: inside the band is calibrated. The band counts each origin once, because the portfolios scored on one day share it. The spread ratio is `1 / sqrt(mean squared standardized error)` over all trials, against the target 1; below 1 the scenarios are too narrow. The CRPS skill is the median per-trial reduction of the cell's CRPS against `no_fit-cpu`. The PIT figures give each arm's mean histogram per size.
- **Scores** (`scores.png`, `summary.csv`): every score per arm, aggregated per trial over its origins, as a point with its 95 % bootstrap interval. A score where lower is better shows each arm's median paired difference from `no_fit-cpu`, which removes the spread between trials that every arm shares; a score with a target (spread, coverage, correlation bias, VaR exceedance) shows each arm's mean over trials against the target.
- **Comparisons** (`comparisons.csv`): every arm against `no_fit-cpu`, and each simulator's GPU arm against its CPU arm, with the median paired difference, its bootstrap interval, and a Wilcoxon signed-rank p-value.
- **Calibration** (`calibration_pit.png`, `calibration_reliability.png`, `reliability.csv`): mean PIT histograms, and the empirical against nominal coverage of central intervals.
- **Horizons** (`horizons.png`, `portfolio_horizons_<kind>.png`): every reading as a curve over the horizons, drawn per panel as in the other figures. `horizons.png` holds the scores and skills of `scores.png` and `skill.png`; each `portfolio_horizons_<kind>.png` holds the readings of `portfolio_sizes.png` for one portfolio kind, one column per portfolio size, with the breach rates' binomial bands. The numbers are those of the horizon rows of the other tables.
- **Timing** (`timing.png`, `timing.csv`, `speedup.csv`): seconds per generation call without warm-up, read from the next-day rows, and each simulator's CPU-to-GPU time ratio. A call generates every horizon, so a config's timing compares only with configs of the same horizons.
- **Regimes** (`regimes_<feature>.png`, `regimes.csv`, `origin_features.csv`, `regime_summary.csv`, `regime_comparisons.csv`, `regime_skill.csv`, `regime_ranking.csv`, `regime_portfolio_sizes.csv`): every score, skill, ranking, and portfolio-size reading above, repeated per tercile of three features of the forecast origin, because an average over all origins can hide that an arm gains in one market regime and fails in another. [`regimes.py`](regimes.py) recomputes the features from the returns each origin's arms and scores saw:
  - `window_correlation`: the look-back window's mean pairwise correlation.
  - `volatility_ratio`: each asset's volatility over the window's last 63 returns divided by its volatility over the whole window, median over assets. It is above 1 when volatility rose into the origin.
  - `correlation_change`: the forward returns' mean pairwise correlation minus the window's. It looks ahead, so it explains readings and never selects a forecast.

  Each table holds the overall readings first, with `feature` and `regime` set to `all` and the same values as the overall tables, then one block per feature and tercile (`low`, `middle`, `high`). Within a tercile, each trial is aggregated over its origins in that tercile, and the intervals resample trials. `regimes.csv` gives each tercile's feature bounds and its numbers of origins and trials, and `origin_features.csv` gives each origin's features and terciles. Each figure shows one feature: the first column of every panel holds all origins, the next three the terciles, drawn as in `scores.png` and `skill.png`. The portfolio-size readings per tercile are in `regime_portfolio_sizes.csv` only, since a curve per size, kind, and tercile would not fit one figure.

- **Correlation dilution** (`dilution.png`, `dilution.csv`): how each arm's correlation bias grows with the look-back window's mean pairwise correlation ρ̄. [`dilution.py`](dilution.py) fits each origin's `corr_bias_trailing` on its `window_correlation` by least squares, bias = intercept + slope · ρ̄, over all origins and in every regime above, per horizon. Shrinking every correlation toward a fixed prior ρ₀ with weight λ gives slope −λ and intercept λ·ρ₀, so the line tells the shortfall's shapes apart. An intercept near zero is a proportional dilution toward independence, and a positive one is shrinkage toward a positive prior. `forecast_slope`, 1 + slope, is how much the forecast's correlation rises per unit of the window's; 1 keeps it. Each row gives the numbers of trials and origins and every coefficient with its 95 % bootstrap interval, which resamples trials and refits on their origins. The figure draws each simulator but `no_fit-cpu`, whose next-day bias is zero by construction, at the next day: every origin as a point, the line over all origins, and its band. Points that fall ever further below the line at high ρ̄ show a ceiling on the correlation an arm can express, which the straight line hides. Among few trials, a resample can draw one trial holding a single origin and nothing else, which fits no line. `undefined_resamples` counts such resamples, and where it is above 0 the cell's intervals are empty (NaN) and its panel has no band, since dropping them would narrow the interval exactly where trials are too few.

- **Swap effects** (`swap_effects.csv`, `swap_effects_horizons.png`, `swap_effects_portfolio_sizes.png`, only when the results hold the three [dependence swap arms](#dependence-swap-arms)): every score and portfolio reading split per trial into the main effect of JointFM's marginals, ((JJ − WJ) + (JW − WW)) / 2, the main effect of its dependence, ((JJ − JW) + (WJ − WW)) / 2, and their interaction, (JJ − WJ) − (JW − WW). Cells are named with the marginal source first: J is JointFM and W is the window. A `construction` row gives the window corner minus `no_fit-cpu`, which should be zero within noise. Each row gives the mean over trials, its 95 % bootstrap interval, and a Wilcoxon p-value. It reports means rather than the medians of the comparisons, because means add up, so the marginal and dependence effects sum to the mean difference between JJ and WW, and because a reading that changes in only some trials keeps its effect: over a few origins per trial a breach rate takes few values, and its median per-trial effect reads zero. The figures draw each effect in place of an arm, as a point with its interval against zero: `swap_effects_horizons.png` the scores of `horizons.png` over the horizons, and `swap_effects_portfolio_sizes.png` the next-day portfolio readings over the portfolio size, laid out as `portfolio_sizes.png`. Its rows are the readings the effects split, each cell's breach rates, CRPS, and mean squared standardized error, rather than the spread ratio and CRPS skill that `portfolio_sizes.png` derives from them.
- **Independence control** (`independence_control.csv`, `independence_control_horizons.png`, `independence_control_portfolio_sizes.png`, only when the results hold `window-independent`): every reading of the swap effects, as `window-independent` minus `no_fit-cpu` per trial, which shows how far each reading moves once all dependence is removed. Each row gives the mean over trials, its 95 % bootstrap interval, and a Wilcoxon p-value, as the swap effects do and for the same reasons, and the figures draw it as the swap-effect figures draw an effect.

Colors follow the simulator. Filled marks are CPU arms and hollow marks GPU arms, and every axis label names its arm.

### Where each arm is drawn

Every per-arm figure of both reports draws the scenario simulators only. Each measurement arm is drawn only in the figure that reads it, so its readings neither crowd the simulators' panels nor set their axes: the control's breach rates and correlation bias lie far from any simulator's, and a swap cell would draw over the donor whose values it keeps. The tables keep a row for every arm, except the ranking.

| Arms | Figures |
| --- | --- |
| Simulators: `no_fit-cpu`, `gaussian-cpu`, `kde-cpu`, `kde-gpu`, `jointfm-cpu`, `jointfm-gpu` | Every per-arm figure of both reports |
| [Dependence swap arms](#dependence-swap-arms) | `swap_effects_horizons.png`, `swap_effects_portfolio_sizes.png`, `rebalancing_swap_effects.png` |
| `jointfm-historical` | `rebalancing_mean_attribution.png` |
| `window-independent` | `independence_control_horizons.png`, `independence_control_portfolio_sizes.png`, `rebalancing_independence_control.png` |

## Paired comparison

```bash
task experiments:paired BASELINE=experiments/simulator_comparison/configs/pilot.yaml CONFIG=experiments/simulator_comparison/configs/pilot_long_history.yaml SETTING=look_back RESULTS=scenario
```

Reads what one setting changes, from the results of two configs that differ only in that setting and their output files. Both draw the same trials, origins, and seeds, so their rows pair trial by trial, and [`paired.py`](paired.py) reads, for every arm both files hold and every reading, the change from the `BASELINE` run to the `CONFIG` run. `SETTING` names the setting, and `RESULTS` which results file of each config to compare: `scenario`, the config's `output`, or `rebalancing`, its `rebalancing.output`.

| `SETTING` | `RESULTS` | What differs | Twin pair |
| --- | --- | --- | --- |
| `look_back` | `scenario` | The history every arm receives | `pilot.yaml` and its long-history twin |
| `horizons` | `scenario` | The horizons each origin is scored at; the files pair at the horizons both hold | `pilot.yaml` and its next-day twin |
| `risk_aversion` | `rebalancing` | The base risk aversion of the backtest | The base and its risk-averse twin |
| `checkpoint` | either | The checkpoint the JointFM services serve | One config run once per served checkpoint, each time into its own output files |

- **History**: every arm gets the longer history, not only JointFM, because the correlation bias reads each arm against the window it saw: with JointFM alone on a longer history, its bias would mix what it keeps of the dependence with the difference between a long and a short window's correlations.
- **Horizons**: JointFM answers every horizon in one request, so its next day can change with the other horizons it is asked for. Every other arm draws the same next day either way, so its change reads exactly zero.
- **Checkpoint**: a JointFM service reports the label it was started with, which stays the same when the weights behind it change, so this setting also accepts two files that record the same service; only the person who served them knows whether the weights differ. The two service records may differ in any field, the runner image and client version included, but both files must hold the JointFM arm of the same device. The runner refuses to resume a results file under another checkpoint, so run the new checkpoint into a copy of the config that changes only its output files.

`paired.py` refuses two files whose identities differ in anything but the setting, the arms each holds, and the host, and, for every setting but `checkpoint`, two files that hold the same value of it. It writes into the `CONFIG` report directory, the rebalancing one for `RESULTS=rebalancing`:

- `paired_<setting>.csv`: per arm both files hold, reading, and, for scenario results, horizon, the change over trials of the `CONFIG` minus the `BASELINE` reading, with its 95 % bootstrap interval, Wilcoxon p-value, and number of paired trials, after `setting`, `baseline_value`, and `value`. Scenario readings are the scores of `comparisons.csv` and each portfolio cell's breach rates, CRPS, and squared standardized error; rebalancing readings are those of `rebalancing_comparisons.csv`. A reading that is a share of events, a VaR breach rate or an interval coverage, reads its mean change, and every other reading its median change, as named in `statistic`: over a few origins per trial a share takes few values, so its median change reads zero where its mean keeps the change.
- `paired_<setting>.png`: for scenario results, each score's change per arm over the horizons, laid out as `horizons.png`; for rebalancing results, each reading's change per arm, laid out as `rebalancing_differences.png`. Every arm both files hold is drawn, the measurement arms included, since a change between two runs is a reading of each of them.
- `paired_<setting>_portfolios.png`, scenario results only: the change of the next-day portfolio breach rates and CRPS over the portfolio size, one column per portfolio kind, laid out as `portfolio_sizes.png`.

The regime readings of each run split its origins by features of its own window, so they do not pair across runs.

## Rebalancing

```bash
task experiments:rebalance CONFIG=experiments/simulator_comparison/configs/full.yaml
```

This runs each trial's universe through the library's rebalancing backtest (`rebalance_portfolio`), once per simulator in the config's `rebalancing.arms`, and then writes its report to `<rebalancing output stem>_report/`.

- **Trials:** `rebalancing.trials` sets the count independently of the scenario comparison. Trial `i` trades the assets of scenario trial `i`, drawn from the experiment seed and `i` alone, so the trials both run share their universes.
- **Trading window:** each trial draws its own window of `trading_days` from its seed.
- **Rebalancing rule:** after every `look_forward_window` trading days, `trigger` decides whether the portfolio is re-optimized, with the configured transaction cost and CVaR constraints. `every_step` re-optimizes every time, a fixed calendar that gives every arm the same decision dates, so arms differ only in their scenarios and expected returns. `pct_change` re-optimizes only when the step's return, or the sum of the losing steps since the last re-optimization, falls below `pct_change_threshold`.
- **Risk aversion:** the configured base is scaled once per trial on the history before the window, as the rebalancing notebook does. The runs keep that value, with no per-window scaling.
- **Cash:** cash earns the daily 3-month Treasury bill rate from `rebalancing.risk_free_rates`, which `task data:risk-free-rates` downloads from FRED (series DTB3). Every optimization credits cash with the rate quoted on its date, the backtest accrues the rate day by day, and the Sharpe and Sortino ratios subtract it. A day earns the rate quoted before it, compounded over 252 trading days a year.
- **Pairing:** all arms of a trial share the window, constraints, risk aversion and scenario seed.
- **Arms:** the device changes only speed, not the portfolios, so one arm per simulator is enough. `jointfm` reaches the service `.env` selects.

Each run records:

| Group | Readings |
|---|---|
| Per step | Mean step return (average PnL per step) and step-return volatility |
| Over the window | Total simple return, annualized return and volatility, maximum drawdown |
| Risk-adjusted | Sharpe and Sortino ratios against the daily risk-free rate, Calmar ratio |
| Trading | Turnover and rebalance count |
| Baseline | Buy-and-hold return of the first portfolio |
| Path | The per-step returns |
| Chosen portfolios | Per decision: the chosen portfolio's one-day scenario VaR and CVaR at the optimizer's `confidence`, its scenario mean and standard deviation, its effective number of holdings, and, over the days it is held, its VaR breaches and squared standardized returns. Per run: the breach rate, the ratio of realized to scenario volatility, and the effective holdings averaged over the held days |

The report compares every reading of every arm with `no_fit-cpu`, paired by trial. It plots, for the simulators only ([Where each arm is drawn](#where-each-arm-is-drawn)):
- every reading's median paired difference from `no_fit-cpu` with its 95 % bootstrap interval (`rebalancing_differences`);
- the mean cumulative return after each step (`rebalancing_paths`);
- the risk of the chosen portfolios over the size curves of random portfolios (`rebalancing_chosen_risk`), described below.

`rebalancing_chosen_risk.csv` reads the risk of the portfolios each arm chose ([`chosen.py`](chosen.py)). An optimizer seeks out the portfolios whose risk its scenarios understate most, which the random portfolios of the portfolio scores cannot show. A decision holds its portfolio from the day after it until the next decision, and the scenario and realized returns both follow the portfolio scores' convention: simple returns aggregated by weight, cash earning nothing. The effective number of holdings, `(sum |w|)^2 / sum w^2` over the asset weights, is `n` for `n` positions of equal size, so a chosen portfolio's readings can sit next to the portfolio-size curves. Per arm, the table gives the share of held days that breach the VaR, with its bootstrap interval over trials and the binomial band of a correct VaR, and the realized-to-scenario volatility ratio with its interval. Every arm understates the risk of the portfolio it picks, so `no_fit-cpu`'s row, not the nominal rate, is the reference. Results files recorded before the chosen-portfolio record existed cannot be resumed or reported; rerun them from scratch.

`rebalancing_chosen_risk.png` ([`chosen_report.py`](chosen_report.py)) draws that table over the next-day curves of the random long-only and long-short portfolios, so each arm's chosen portfolios read against random portfolios of the same size under the same simulator's scenarios. Rows are the 95 % breach rate and the spread on the size curves' scale, scenario over realized, which is the reciprocal of the volatility ratio. Columns are the two portfolio kinds. Each arm's chosen portfolios are a diamond at their mean effective number of holdings, with their interval and, on the breach panels, a hatched band of a correct VaR over the held days. The curves are those of the scenario arms of the same simulators, recomputed over exactly the backtested trials and written to `rebalancing_size_curves.csv`. They come from the scenario results file named by `rebalancing.scenario_results`. Each config names its own `output` there, and a risk-averse twin, which runs no scenario comparison of its own, names its base's. The report refuses a file that is missing, was measured on other prices, drew its random portfolios within other weight, cash, or leverage bounds than the optimizer's, lacks a complete record of a backtested trial, or trades another universe in one. So the scenario comparison must run before the rebalancing report; `task experiments:all` runs them in that order.

With the three dependence swap arms it also writes `rebalancing_swap_effects.csv`, which splits every reading as `swap_effects.csv` does, and draws it as `rebalancing_swap_effects.png`: the panels of `rebalancing_differences.png` with each effect's mean and interval in place of an arm.

With `jointfm-historical` it also writes `rebalancing_mean_attribution.csv` ([Rebalancing attribution](#rebalancing-attribution)), which splits every reading's difference between `jointfm` and `no_fit-cpu`, per trial, into an `expected_returns` part, `jointfm` minus `jointfm-historical`, and a `scenarios` part, `jointfm-historical` minus `no_fit-cpu`; a `total` row gives the difference itself. Each row gives the mean over trials, its 95 % bootstrap interval, and a Wilcoxon p-value. It reports means rather than the medians of the comparisons, because means add up: the two parts' means sum to the total's. `rebalancing_mean_attribution` draws the table with the panels of `rebalancing_differences`, the total and its two parts in place of the arms, each a mean with its interval against zero, so a reading whose total sits with one part shows which of JointFM's two differences moves it.

With `window-independent` it also writes `rebalancing_independence_control.csv`, every reading as `window-independent` minus `no_fit-cpu` per trial with its mean over trials, interval, and p-value, and draws it as `rebalancing_independence_control.png` with the panels of `rebalancing_differences.png`. Whether a reading can see dependence at all reads off it: a reading the control does not move beyond its interval cannot judge a simulator's dependence.

Rerunning resumes the results file and re-renders the report; `task experiments:rebalance-report` re-renders it without running anything. Portfolio values follow the library's backtester, which compounds the portfolio's simple returns as `cumprod(1 + R @ w)`, so a short position's full loss reaches the value.

## Universe sizes

```bash
task experiments:universe-sizes CONFIG=experiments/simulator_comparison/configs/full.yaml
```

Reads how each simulator's rebalanced portfolio changes with the number of assets it trades. [`universe_sizes.py`](universe_sizes.py) runs the rebalancing backtest of [Rebalancing](#rebalancing) once per trial, size of `universe_sizes.sizes`, and simulator of `universe_sizes.arms`, over `rebalancing.trials` trials, and writes one row per run to `universe_sizes.output`. The task then writes the [blog figures](#blog).

- **Nested universes:** each trial fixes one random order of its assets, from the experiment seed, the trial index, and a stream of its own, and a size trades the first ones of that order. Every smaller universe is thus a subset of every larger one, and the size equal to `assets` trades exactly the rebalancing backtest's universe, run for run.
- **Pairing:** every size and simulator of a trial share its trading window, scenario seed, and rebalancing settings, so a trial's readings differ across sizes only in the assets traded. Each size calibrates its risk aversion on its own assets, as a trial of that size would.
- **Results:** the columns of the rebalancing results plus `size`. The run resumes its file and refuses one measured under other conditions, as the rebalancing backtest does; more trials or sizes extend it.
- **Cost:** the run at the size equal to `assets` costs what the rebalancing run of the same simulator costs; a smaller universe means smaller scenario requests and optimizations. The pilot's sizes measure how the cost grows with the size.

## CPU against GPU

```bash
task experiments:devices GPU_URL=http://127.0.0.1:8080 CPU_URL=http://127.0.0.1:8081    # devices.yaml, resuming its results, then its report
task experiments:devices-fresh GPU_URL=http://127.0.0.1:8080 CPU_URL=http://127.0.0.1:8081 CONFIG=experiments/simulator_comparison/configs/devices_pilot.yaml    # the pilot from scratch
task experiments:devices-report              # its report again, without running anything
```

Measures what one rebalancing decision costs on each device, stage by stage. [`devices.py`](devices.py) runs every decision of the first `trials` trials of the backtest that the configuration's `experiment` sets up, on its universes, trading windows, prices, cash rates, trigger, and CVaR constraints, through the library's `rebalance_portfolio`, once per device:

- **GPU session:** JointFM on the local service at `GPU_URL`, and `gpu_solver` (cuOpt PDLP) on the GPU that service computes on.
- **CPU session:** JointFM on the local service at `CPU_URL`, and `cpu_solver`, in a process started with `CUDA_VISIBLE_DEVICES` empty, so nothing in it reaches a GPU.

Each URL is set as `JOINTFM_LOCAL_BASE_URL` over `.env`, so `.env` must use the local selector or none, because selectors from the process and `.env` count together.

- **Stages:** a stand-in for the backtest's scenario generator and decision observer (`StageClock`) times each decision without changing the library. Scenario generation is the generator's call, including the HTTP round trip to the service; the optimizer runs from that call's return to the chosen portfolio, through the problem's setup and solve; the decision's total is their sum.
- **Same problems for every solver:** CPU and CUDA random generators draw differently for the same seed, so the two pipelines optimize on different scenarios, and their backtests drift apart. After each trial, the GPU session therefore rebuilds every decision's problem from the scenarios, expected returns, and previous portfolio its backtest optimized on, and solves it with every `paired_solvers` solver ([`solvers.py`](solvers.py)), timing setup and solve and keeping each solution. cuOpt's methods solve to different default accuracies (PDLP 1e-4 relative, dual simplex 1e-6 absolute, barrier 1e-8), so the report gives each solver's largest weight and objective distance from `gpu_solver`'s solution of the same problem. cuOpt barrier factors the augmented system (its `augmented` option) instead of its default normal equations: every scenario row holds every portfolio weight, so the normal equations are dense in the scenarios, and at 50,000 scenarios they asked for more GPU memory than any GPU has.
- **Other simulators:** every simulator of `generators` draws scenarios from each decision's look-back window in the session of its own device, so KDE runs on scikit-learn in the CPU session and on cuML in the GPU session.
- **Services:** start both from the public inference runner on this host, serving the same checkpoint on different ports: in a `joint-inference-python` checkout, `JOINTFM_INFERENCE_MAX_SAMPLE_COUNT=20000 JOINTFM_INFERENCE_DEVICE=cuda:0 JOINTFM_INFERENCE_PORT=8080 task serve` and `JOINTFM_INFERENCE_MAX_SAMPLE_COUNT=20000 JOINTFM_INFERENCE_DEVICE=cpu JOINTFM_INFERENCE_PORT=8081 OMP_NUM_THREADS=<threads> task serve`; variables set in the shell override that checkout's `.env`. The sample cap must reach `num_scen`: at the runner's default of 1,000, the client splits each decision's scenarios into `num_scen / 1000` requests, and every request runs the model once, so the reading would time that many forward passes instead of one. Before its first trial, a session finds its service by the URL's port and refuses a remote URL, a GPU service that computes on another GPU than this process's cuOpt, and a CPU service without `OMP_NUM_THREADS`. It records the service's command line, its thread and device settings, and the CPUs it may run on.
- **Idle host:** other processes on the CPU slow the CPU pipeline and the CPU-side stages of the GPU pipeline, so stop every other job for the run. Each trial records `foreign_cores`, the mean CPU cores the host's other processes used while it ran.
- **Pilot:** [`devices_pilot.yaml`](configs/devices_pilot.yaml) runs the first trial. Run it from scratch at each candidate thread count of the CPU service, such as its physical cores and all its hardware threads, keep the fastest, and set `cpu_solver` to the fastest CPU solver of its `solvers` table.
- **Results:** one row per decision, generation call, and solve, told apart by `kind`; [`devices.py`](devices.py) describes the columns of each. The first row of each kind and name in a process is flagged `warmup`. A session's trial is written once complete, so a rerun resumes after the last complete trial of each session, and a file measured under other conditions is refused.
- **Report:** [`devices_report.py`](devices_report.py) writes three tables and their figures to `<output stem>_report/`: `runtime`, `runtime_devices`, and `solvers` ([Blog](#blog)). It reads the trials both sessions finished, and every table names the host's CPU and the GPU session's GPU.

## Blog

```bash
task experiments:blog CONFIG=experiments/simulator_comparison/configs/full.yaml
```

The two reports draw every reading of every arm, so they show where JointFM needs to improve as much as where it leads. [`blog.py`](blog.py) draws only the readings a blog post about JointFM builds its story on, from a config's scenario results and rebalancing results and from the [CPU-against-GPU](#cpu-against-gpu) results of [`devices.yaml`](configs/devices.yaml) (`DEVICES_CONFIG`), into `<output stem>_blog/` beside the scenario results: `pilot_blog/` for the pilot, `full_blog/` for the full set. That folder holds the blog's figures and nothing else: each figure as PNG and SVG, and a CSV of exactly the numbers it draws, which is what the post's text cites. `experiments:all` writes it last, so `experiments:pilot` and `experiments:full` both produce it; it needs the scenario, rebalancing, and universe-size results files, so a twin config has none. It also needs the CPU-against-GPU results of both sessions, so run `experiments:devices` once before the first blog; until then the blog stops with an error that names it.

| Figure | Reading | Results |
| --- | --- | --- |
| `ranking` | Each simulator's share of trials with the best next-day energy score and portfolio CRPS, and its mean rank | Scenario |
| `skill_horizons` | Energy-score and CRPS skill against `no_fit-cpu` over the horizons: median over trials with its interval | Scenario |
| `growth` | Mean cumulative return and the mean of each trial's drawdown from its own running peak at every rebalancing date | Rebalancing |
| `risk_return` | Each simulator's mean annualized volatility against its mean annualized return as a dot, with cash at the backtests' mean risk-free return and the frontier with cash: the line from cash through the simulator whose line from cash is steepest, which any mix of that simulator's portfolio with cash reaches (solid) or reaches by borrowing at the risk-free rate (dashed). The area below it is shaded. | Rebalancing |
| `performance` | Annualized return and volatility, Sharpe, Sortino, maximum drawdown, and Calmar ratio per simulator, and the trials in which each beat `no_fit-cpu` | Rebalancing |
| `universe_sizes` | Each simulator's mean total return over the universe sizes, as lines without intervals: the trading windows' market moves spread every simulator's level alike, so intervals of the levels overlap even where the paired differences are clear. JointFM is drawn bold, the other simulators thin over the band between their lowest and highest mean. The CSV holds total return and maximum drawdown, which the post's text cites, in two kinds of rows (`reading`). `size` rows give each size's means and the differences from `no_fit-cpu`, with their intervals, p-values, and the trials each simulator did better in. `change` rows, without a size, give the same readings of each trial's change from the smallest to the largest size: the least-squares slope over all sizes times their span, so a simulator that gains nothing from more assets reads about zero. | Universe sizes |
| `runtime` | Mean seconds per scenario-generation call of every simulator on every device it ran on, at the rebalancing decisions, with its interval over trials | CPU against GPU |
| `runtime_devices` | Mean seconds per rebalancing decision on each device by stage (JointFM's scenarios, the optimizer, the total), and the median per-trial ratio of CPU over GPU seconds of each, with their intervals | CPU against GPU |
| `solvers` | Mean seconds per solve of every paired solver on the decisions' identical problems, its median per-trial time over `gpu_solver`'s, and the largest weight and objective distance of its solutions from `gpu_solver`'s | CPU against GPU |

- **Same numbers as the reports.** Every statistic comes from the functions the reports use, so a blog number equals the report's reading of the same arm, score, and horizon. The ranking ranks the drawn simulators only.
- **Simulators only, by their blog names.** The figures draw one arm per scenario simulator, named as the post names them: Historical (`no_fit`), Gaussian, KDE, and JointFM. A simulator that ran on both devices is drawn by its GPU arm, except in the CPU-against-GPU figures, which compare the devices. The measurement arms appear in the reports only.
- **Hardware named.** Every CPU-against-GPU table names the host's CPU model, sockets, and cores, and the GPU of the GPU session, as the results recorded them; the post's captions name them for the figures.
- **Titles state what is drawn, never a finding.** The same figures re-render from every run, the pilot's and the full set's, and from every served checkpoint, so a caption that states a result belongs in the post, next to the numbers of the CSV it read.
- **No text below the axes.** Beyond a figure's title, subtitle, axis labels, and legend, its description (sample sizes, what a label counts, what a line or shading means, the hardware) lives in the post's caption only, so the figure and its caption never state it twice or differently. The CPU-against-GPU figures of `devices_report.py` share this, since the blog draws them with the same functions.
- **Drawdown at rebalancing dates.** The results keep one return per step, so `growth` reads the drawdown at step ends; the `max_drawdown` of `performance` reads it over daily values and can be deeper.
